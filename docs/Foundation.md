For Together there will be two main threads running simultaneously in parallel at runtime. One will be the audio thread where we will get the data of the audio and the other one will be our main program thread. Data will be shared between them both. 

The main workflow
This audio thread is the flow that connects from input hardware to output hardware. Throughout this flow we will sample the data to our program thread, modify the data anyway we want, then send it back to the audio thread before its output.

One important thing is that one frame cant wait for the other, there must be a standard way to send and receive data from both threads. We cant stop one thread while it waits for the data of the other since its realtime audio, the flow must continue. That is why we'll use a callback model. This basically means that we have a callback function that is ran by the api on each cycle of the audio thread. That means that in every iteration of the audio thread, we will run our main function. Its important to mention that the threads cant be interrupted with locks, one thread waiting for another because that would freeze the flow from one thread completely killing performance and making the program or sound slow or even worse, completely freeze. Its also important to avoid memory allocation entirely since waiting for the os to allocate memory adds a layer of uncertainty and risks missing the deadline entirely, that is why we have memory pools preallocated.

Now the next question is how fast are this cycles? thats where the latency/stability tradeoff comes in.
The program will have a max audio frequency of 48000 samples per second. A sample is just a snapshot of the wave at a certain time. The closer we want to be to real time audio, the closer we have to arrive to these samples per second. This samples are grouped in specific sample size clusters that are then sent to a specific placeholder named a buffer. Then the other thread reads this buffer to receive the data. We cant edit live data in one thread because that would corrupt the data.

Now with this buffer size we have a deadline limit for our main thread. The smaller we make this buffer size the smaller our window of time will be to edit the data in that buffer. We can determine this deadline by the cluster size divided by the max audio frequency. A good starting point is 256 samples. So 256/48000 which are 0.005 seconds or 5ms. So our main thread has this much time to make the edits for this buffer before it finishes. The issue is that if it doesnt finish in time, the audio starts to pop. Since it has to skip a few buffers before it can return the edited data to the buffer and the audio thread can pick it back up. 

So the tradeoff is, make the buffer too small and the audio is closer to realtime but the probability of popping is increased, or make the buffer too big and the probability of poping is lower but it has more delay.

Now the audio thread flow is hardware drivers, alsa, api, our program, back to the audio thread and back to hardware output. To sample the data to our program we use the API, This is where we JACK comes in.
We first register our callback function to the api using the jack_set_process_callback() function, then we access the audio sample inside the callback with jack_port_get_buffer(). Finally we query the current buffer size with jack_get_buffer_size().

As for Linux audio apis the two main ones are PipeWire and JACK. Jack was purpose built for high performance audio engineering, the workflow is straightforward and its faster. PipeWire is more a standard server that connects other apis. Pipewire has a JACK API built in that converts jack instructions. That means that it can use jack without an issue. We decided to use JACK.
